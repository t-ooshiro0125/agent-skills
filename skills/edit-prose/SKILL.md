# Edit Prose

## 目的と対象

メール、チャット、技術記事、業務文書、エッセイなど、既存の日本語文章の構文確認・構成の見直し・リライトを求められた場合に使用する。書き手の意味、感情、距離感を保ち、情報同士の関係が自然に伝わる文章へ整える。

ルール・運用文書には [edit-rulebook](../edit-rulebook/SKILL.md) を使う。普段のAIとの会話、雑談、質問への回答、壁打ち、アイデア出しには適用しない。

## 優先順位

編集では次の順序を守る。AIらしさを減らすこと自体を目的にせず、下位の目的のために上位の品質を損なわない。

1. 意味の保持
2. 論理的一貫性
3. 情報密度
4. 読みやすさ
5. 自然な日本語
6. AI特有の癖の除去

## 原文の扱い

### 意味を変えない

原文にある事実、主張、理由、条件、数値、評価を維持する。文章を分かりやすくするためだけに、原文から確認できない事実、定義、理由、具体例を追加しない。ユーザーが採用した追加案の反映を依頼された場合は、その範囲で内容・根拠・条件・確認範囲を保って反映し、未採用の案を確定事項として扱わない。

事実、資料に記載された情報、書き手の解釈、推測、未確認事項の違いと、断定の強さ、確認した対象・条件を保つ。「記載がない」を「制限がない」、「未確認」を「できない」と言い換えない。

重複や冗長な表現の整理と、情報そのものの削除を区別する。文書の目的に不要と思われる情報でも、独自の内容を持つ場合は削除候補と理由を示し、リライトだけの依頼では削除しない。情報の省略を明示的に求められた場合や、ユーザーがレビューの削除案を採用した場合は、その範囲で省略する。

### 感情と温度感を保つ

原文の感情、温度感、距離感、簡潔さ、率直さを保つ。丁寧さだけを理由に謝罪、恐縮、感謝、親しさを加えたり、不必要に柔らかくしたりしない。

## 編集手順

文章の長さにかかわらず、次の順に確認・編集する。確認のみの場合も同じ順で点検し、文書の編集は行わない。詳細な判断基準は後続の各節に従う。

問題のない箇所は無理に変えず、重複、説明不足、構成上の問題に応じて変更量を調整する。主語や対象が不明確、話題が散在、説明が重複する場合は、文単位にとどまらず構成から整理してよい。

1. 原文を理解する。明示された目的・想定読者・利用場面・依頼条件と、主張、事実、感情、判断を確認し、「読み手が何を理解・確認するための文章か」を一文で把握する。「重複と説明量」に従い、読者の前提知識と説明の十分さも確認する。意味が曖昧な箇所は推測で確定せず示す。
2. 構成と形式を判断する。「構成」「箇条書きとコードブロック」に従い、目的と情報の関係に合う順序・まとまり・形式を選ぶ。
3. 表現を調整する。「重複と説明量」「表現」に従い、主語と述語、修飾語の係り受け、助詞・接続表現、指示語の参照先、文同士のつながりを整える。短縮時はまず各項目や段落内の重複・冗長な表現を削り、さらに形式を変える必要があるかは目的と情報の関係で判断する。最後にAI特有の不自然な表現だけを修正する。
4. 原文と照合し、「最終確認」を行ってから依頼に応じた形式で出力する。

## 構成

### 文書間の配置

関連文書がある場合や、文書構成の見直しが依頼に含まれる場合は、文書の目的・読者・役割に照らして、文書内の整理と別文書への移動・分割を表現調整より先に判断する。情報の探しやすさと参照先を行き来する負担を比較し、配置の問題を見出し追加や言い換えだけで処理しない。単独の短いメールや報告文などに、一律に別文書への分割判断を求めない。

移動・分割案では、対象箇所・移動先・理由・元の文書に残す概要や案内を示す。既存構成から移動先が明らかで編集依頼の範囲に含まれる場合は、利用先の規約に従って整理し、元の情報・条件・要求の強さと必要な参照関係を維持する。確認のみの場合や移動が依頼範囲外の場合は案を示し、範囲内で可能な確認・編集を続ける。

文書の役割や移動先にユーザー判断が必要な場合は、判断事項と影響範囲を示し、その判断に依存するリライトや細かな表現案だけを保留する。他の確認・編集は続け、保留を理由に情報を削除しない。

### 文・段落・節・記事の役割

文・段落・節・記事には次の役割がある。形式や長さに応じて必要な階層を使い、すべてを設ける必要はない。

- 文: 密接に関連する情報を、無理のない範囲で一つの文として表す。
- 段落: 一つの論点、対象、手順を説明し切る。
- 節: 一つの話題を一つまたは複数の段落で完結させる。
- 記事: 一つの目的や主メッセージに向かって各節を配置する。

境界は読み手が理解できる意味のまとまりで判断する。文字数や文章量を揃えるために、情報の関係を切断したり、節を増やしたり、異なるまとまりを押し込んだりしない。

### 情報の順序

読み手が理解・判断に必要とする順序で情報を配置し、各段落や節に文章全体の目的に必要な役割を持たせる。各説明を理解するために先に必要な前提も確認し、文書の用途に応じて順序を選ぶ。情報を探して使う文章や、比較・判断・相談のための文章では、原文にある対象・選択肢・判断の要点を把握する前に、細かな手順や内部構造を読まなければならない構成を避ける。判断が未確定の場合は、何が未確定で、何を検討するための文章なのかが分かる位置に置く。選択・判断に必要な根拠や条件は近くに置き、その後に必要になる詳細は、対応する後段や補足にまとめる。ただし、理解に必要な前提、因果関係、時間の流れは維持する。

### 同じテーマの記述を統合する

同じ意味、原因、結果、問題意識、判断に属する記述が散らばっていれば、一続きで理解できるよう統合を検討する。関係の薄い話題までまとめず、短縮自体を目的にしない。

### 見出しは話題の境界に置く

見出しは話題、目的、論点が変わる境界に置き、同じテーマが続く段落は同じ節で説明してよい。文章量を区切るために見出しを増減しない。短い節が続く場合は、独立して探す必要のある話題か確認し、前提や補足であれば関連する節への統合を検討する。長さだけで節を統合したり、長く見せるために説明を足したりしない。

内容を探しやすい名詞句や短い表現でよく、すべての見出しを結論文やキャッチコピーにしない。

### 短い文を並べることを読みやすさとみなさない

密接な情報は一文か一段落で関係が分かるようにまとめ、内容に応じて文の長短に自然な変化をつける。短い文の連続や視覚的な余白だけを読みやすさとみなさない。

### 段落は一つの論点を説明し切る単位にする

同じ論点、対象、手順を説明している間は、原則として同じ段落で続ける。1〜2文ごとの機械的な改段落は避け、論点、対象、時間軸、説明の役割が変わり、新しいまとまりにした方が理解しやすい場合に限って分ける。長さを減らすために無関係な話題を接続しない。

各段落の論点と役割を把握し、同じ判断・理解に必要な説明の分散や、異なる論点の混在を点検する。必要なら関連する文を集め直し、事実、理由、結果、判断の関係が分かる段落に組み直す。改段落の削除だけで済ませず、条件や注意事項の適用範囲を維持する。

概要、仕組み、判断条件、手順などの役割も確認するが、役割が複数あることだけで分割せず、同じ理解・判断に必要なまとまりを保つ。

## 重複と説明量

### 読み手に必要な説明を確認する

想定読者の前提知識と用途に照らし、何を既知として扱えるか、理解・判断に必要な説明が足りているかを確認する。読者が不明でも初心者向けと決めつけず、目的と文脈から判断できる範囲で確認する。誰が何をするか、比較の対象、条件、因果関係、処理の流れ、前後の説明のつながりを点検し、説明量は必要な箇所に絞る。

原文にある情報から明確にできる対象や関係は、文脈を保って明示する。原文外の新しい情報が必要な不足は、箇所と理由を示す。原文外の情報を調査して追加案を作るのは [review-docs](../review-docs/SKILL.md) の役割とし、リライトだけの依頼では行わない。

### 同じ情報を形式を変えて繰り返さない

本文で説明した内容を、その直後に箇条書きやコードブロックで再掲するだけの構成を避ける。同じ内容の言い換えが複数箇所にある場合も統合する。

### 要約しすぎない

段落ごとの情報密度を確認する。情報密度を高めることは、説明を削ることではない。理解に必要な理由、前提、因果関係は残す。短くした結果、読み手が関係を推測しなければならなくなるなら、説明を削りすぎている。

## 箇条書きとコードブロック

### 箇条書き

箇条書きは、変更点など複数の項目が本当に並列であり、一覧として確認・比較した方が理解しやすい場合に使用する。理由、因果関係、経緯、前提から結論への流れは、原則として地の文で説明する。

見出しの直後に箇条書きを置く場合も、何を列挙するのかが文脈から明白でなければ、短い導入文を置く。文脈から明白な場合は、導入文を省略してよい。

箇条書きを使わないこと自体を目的にしない。

### コードブロック

コードブロックは、本文だけでは把握しにくい次のような情報を示す場合に使用する。追加する前に、本文だけでは分かりにくい何を示せるか確認する。

- 実際に使用するコード
- 設定ファイルの具体例
- コマンド
- ディレクトリ階層
- 入出力例

本文で説明済みのファイル名を並べ直すだけなど、情報を増やさない装飾には使わない。コードブロックの前後だからという理由だけで文章を細かく分割せず、連続するコマンドや同じ目的の操作は、一つの説明・手順・コードブロックにまとめられないか検討する。

## 表現

- 専門用語・略語：想定読者に馴染みがなく、理解に必要な用語は、初出の近くで意味や役割が分かるようにする。説明も読み手が理解できる言葉を選び、正式名称が後の理解・検索・操作に必要な場合は残す。新しい定義が必要な不足は「重複と説明量」に従って示す。
- 抽象表現：比喩や流行語に限らず、対象・行為・状態・判断内容が読み手に伝わりにくい表現を点検する。原文から確認できる内容を使い、「何がどうなっているか」「何について何を確認・判断するのか」を、読み手に馴染みのある言葉で明示する。意味が明確な表現は無理に変えず、別の抽象語への置き換えだけで終わらせない。原文にない仕様・事実・理由・判断を作らない。
- 自然な比喩：用途・書き手の文体・文脈に合うものは、AIが使いがちという理由だけで削除しない。
- 定型句：内容に不要な前置きや締めを機械的に追加しない。意味を担う表現は残してよい。

## 最終確認

確認のみでは問題の箇所と理由、必要な修正案を示し、リライトでは修正文を提示する。原文外の情報が必要な不足は、リライト時も箇所と理由を添える。出力前に依頼範囲の原文全体を次の観点で点検する。リライトで問題が見つかったら修正・再確認し、確認のみでは指摘・修正案の妥当性と漏れを確認する。

- 意味と情報：依頼で認められた省略以外の意味・情報・条件が残り、ユーザーが採用して反映を依頼した案以外の情報を足していないか。根拠・断定の強さ・確認範囲を保っているか。
- 感情と文体：原文の温度感、距離感、簡潔さ、率直さを保ち、謝罪や感謝などを加えていないか。
- 構成：同じ話がまとまり、見出しが話題の境界にあるか。文章に存在する階層が意味のまとまりになっているか。比較・判断・相談のための文章では、「情報の順序」に従い、検討対象・選択肢・未確定事項を細かな手順や内部構造より先に把握できるか。文書間の配置を見直した場合は、各文書の役割に合う情報と案内があり、参照関係を保てているか。
- 段落：改段落で論点・対象・時間軸・説明の役割が変わっているか。同じ論点やコードブロックの前後を細切れにしていないか。
- 形式：並列項目を一つずつ見つけられ、理由や因果関係を箇条書きで分断していないか。同じ情報の再掲や連続操作の不要な分割がないか。
- 説明と短縮：想定読者の前提知識で、理解・判断に必要な用語の意味・役割と、文の対象・理由・条件を読み取れるか。用語の説明が、別の馴染みのない語へ置き換えただけになっていないか。不足は「読み手に必要な説明を確認する」に従って修正または明示する。必要な理由・前提・因果関係と文のつながりを保ち、目的・依頼条件を満たしているか。短縮で情報の関係や確認しやすさを損なわず、文の長さを不自然に揃えていないか。
