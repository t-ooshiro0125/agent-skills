# Implementation Challenge

## 目的と対象

レビュー結果とその後の議論に対して反証を試み、実装前に手戻りにつながる問題を見つける。現在の会話にあるレビュー結果と議論を使用し、その結論を検証対象とする。全面的な再レビューは行わない。

ファイル編集、実装、マイグレーション、push などは行わない。ファイル参照・検索・テスト実行は行ってよい。

## 検証の方針

破綻条件、不足している前提、確認すべき一次情報を特定する。指摘には、検証対象の結論・前提と、それを覆す具体的な根拠や成立条件を示す。指摘すること自体を目的に、根拠のない問題を追加しない。

調べれば決まることは自分で調べる。反証の判定に必要なファイル参照・検索・テスト実行など、実装を変更しない調査は自律的に実施し、確認手順をユーザーへ投げ返さない。既存の情報だけで判定できる場合は、追加の調査は不要とする。テスト実行などが生成物や環境の状態を変更する場合は、その副作用を考慮して調査方法を選ぶ。未確認の懸念は成立した反証と区別し、調査しても決まらない場合に限り、何を確認すれば判定できるかを示す。

解決済み、またはユーザーがリスクを受容した論点は、判断を変える新しい根拠がない限り再提起しない。

同じレビュー結果に対する再実行は、前回の「判定に必要な確認」が解消されたかの確認に限定し、新しい観点を掘り直さない。ただし、検証対象の結論や前提が実質的に変更された場合は、変更された部分も検証する。

## 停止条件

- 反証の対象がコードの挙動ではなく、レビュー文の表現や検証手順だけになったら、その旨を述べて終了する。
- 検証結果を示した時点で終了し、修正案の設計や比較には進まない。

## 出力形式

「成立した反証」「判定に必要な確認」のうち、該当する項目だけを簡潔に示す。

- 成立した反証には、対象の結論・前提と、それを覆す根拠を示す。
- 「判定に必要な確認」に載せてよいのは、調査では決まらないものだけとする。対象は、仕様上の意思決定、ユーザーのリスク受容、外部環境や権限が必要なもの、状態を変える必要があるもの。コードや設定を読めば決まることは、調査して結果を書く。

どちらもない場合は、「検証した範囲では、レビューの結論を覆す根拠は見つかりませんでした。」と返す。
