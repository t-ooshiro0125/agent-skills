# Review Docs Workflow

## 目的と対象

指定された文書の内容を吟味し、その指摘を反証で検証したうえで、構成・表現も確認して改善案を出し揃える。対象文書と確認範囲を特定し、対象が特定できない場合だけユーザーに確認する。ファイルの編集や完成した修正文の提示は行わず、指摘と必要な修正案の提示までで終了する。

内容の確認だけなら [review-docs](../review-docs/SKILL.md)、指摘の再検証だけなら [challenge-docs](../challenge-docs/SKILL.md)、構成・表現の確認やリライトだけなら対応する編集スキルを使う。

## 工程と引き継ぎ

各工程の前に担当スキルの `SKILL.md` を読み、対象範囲・手順・判断基準に従う。工程のルールはここへ複製しない。指定済みの条件は聞き直さず、調べれば決まることは自分で調べる。工程間では停止せず、未確認事項は後続工程へ引き継ぐ。

1. [review-docs](../review-docs/SKILL.md) で、内容の正しさ・不足・不要な記述を確認する。指摘と変更案、それぞれの根拠、未確認事項を保持する。
2. [challenge-docs](../challenge-docs/SKILL.md) に、原文とレビュー結果・根拠・未確認事項を引き継ぎ、反証を試みる。指摘がなければ「対象なし」とし、反論を無理に作らない。
3. 指示・ルール・規約・運用文書は [edit-rulebook](../edit-rulebook/SKILL.md)、日本語の一般文章は [edit-prose](../edit-prose/SKILL.md) を確認のみの依頼として使い、構成・表現の問題と必要な修正案を示す。原文と反証後に残る指摘を引き継ぎ、撤回済みの指摘や解決済みの論点を新しい根拠なく再提起しない。内容変更が未確定の部分は、確定した前提として扱わない。

検証対象がない工程は「対象なし」とし、指摘を無理に作らない。実行環境などの制約による未確認は対象なしと区別して理由を示し、実行可能な確認を継続する。

## 結果の整理と出力

各工程の結果は工程ごとに区切って示し、後続工程の結果で元の指摘を書き換えない。最後に、有効な指摘と撤回・修正された指摘を区別して整理する。後続の調査で解消した確認事項は最終的な未解決事項から外し、未確認事項を検証済みとして扱わない。統合時に新しい指摘や変更の採否を追加せず、本文を不必要に繰り返さずに次を示す。

1. 有効な指摘 — 内容と構成・表現を区別し、必須修正と任意改善に整理する。なければ「なし」
2. 反証で撤回・修正した指摘 — 要点と理由。なければ「なし」
3. 確認結果 — 実施した確認・検証と、そこから確認できたこと
4. 未確認・判断事項 — 残った事項と理由・影響、必要なユーザー判断。なければ「なし」

ユーザーに判断を求めるのは、仕様・方針・リスク受容など調査では決まらない事項だけとし、選択肢と推奨を添える。判断事項がなければその旨を示して終了する。修正・リライトは別途依頼を受けて行い、このワークフローから自動では進まない。文書に記載された業務操作や、外部サービスへの送信・公開も行わない。
