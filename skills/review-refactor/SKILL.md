# Review Refactor

## 目的

実装済みコードから、挙動を変えずに保守しやすくなる箇所や、読んで追いやすくなる箇所だけをリファクタ候補として挙げる。候補の提示までを行い、ファイル編集や実装はしない。

## 対象

- 候補を挙げる範囲は、指定されたコード・ファイル・差分とする。
- 指定がなければ、現在の差分と、差分が触れたメソッド・クラス、その呼び出し元までを対象とする。
- 挙動維持の確認に必要な既存実装・テストは、この範囲の外でも参照してよい。

会話で確定済みの必須修正があれば、修正後の状態を前提にする。現在のコードから確認した事実と修正後の想定を区別し、修正後も残ると合理的に判断できる構造だけを候補にする。修正で解消される問題や不要になる構造は重複して挙げない。修正後の状態を十分に判断できない場合は、推測で候補を追加しない。

## 候補の選定基準

- 「何が保守しやすくなるか」「何が追いやすくなるか」を具体的に説明できるものに限る。
- 既存パターン・規約に沿った小さい変更を優先する。抽象化や共通化を目的にしない。
- 既存コードやテストから、挙動を維持できる合理的な根拠があるものだけを挙げる。実装前の完全な保証は求めないが、根拠が不足するものは挙げない。
- 該当する候補がなければ「リファクタ候補なし」と明言し、候補を無理に作らない。

優先度は、改善効果・変更規模・回帰リスクを総合して判断する。複数箇所の同時修正を減らす効果は重視するが、変更が広範囲に及ぶ場合は慎重に評価する。重複や不要な構造を減らす効果と、小さな変更で複雑な条件分岐や責務を明確にする可読性の改善も評価する。

### 対象外の候補

- 書き方の好み、表記の統一だけが目的の命名変更、効果を説明できない命名変更
- 将来使うかもしれないという理由だけの抽象化
- 大規模な設計変更
- 対象範囲の外にある既存コード
- バグ・仕様不備・テスト不足

### 確認する観点

- 重複した処理や条件
- 責務が混在しているメソッド・クラス
- 読み取りづらい条件分岐
- 意図を把握しづらい命名（既存の規約・命名パターンに沿い、責務や処理の意図が明確になる改善を具体的に説明できる場合）
- 不要な状態や中間変数
- 理解や変更を難しくしている過剰な抽象化・分割・汎用化、不要な処理（既存の仕様と挙動を維持して単純化できるもの）
- 既存の abstraction / helper / concern で置き換えられる処理
- 変更時に複数箇所の同時修正を強いる構造
- テストを不必要に複雑にしている構造

## 挙動維持の確認

確認の範囲と方法は、候補の影響範囲に合わせる。利用先の規約に従い、次のように確認する。

- メソッド内で完結する候補（中間変数、条件分岐の整理など）は、その場のコードから挙動への影響を十分に判断できる場合に限り、追加調査を省略してよい。条件分岐の順序、副作用、例外の発生順序などが変わる可能性がある場合は、挙動維持の根拠を得るために必要な確認を行う。
- 呼び出し関係・メソッド名・公開範囲が変わる候補と、既存実装への置き換えは、呼び出し元と対象を覆うテストを確認する。テストが `skip`、`pending`、タグ除外で外れていないかも確認する。呼び出し元を検索するときは、view からの参照、`send` などの動的呼び出し、別名の helper、文字列で組み立てたパスなど、単純な検索で漏れる参照も確認する。
- 置き換え候補は、置き換え先の実装を読み、挙動が同じと言える根拠を得る。

断定は一次情報を確認した場合だけにする。検索で見つからなかった場合は「見つからなかった」に留める。

## 出力

候補の採否はここでは決めず、すべて任意改善として優先度順に出す。

1. リファクタ候補 — なければ「リファクタ候補なし」
   - `<path:line>`
     - 現状 / 提案 / 理由（何が保守しやすく・追いやすくなるか）
     - 挙動維持の根拠。必要な条件や未確認事項があれば明示し、確認した事実と実装後の見込みを区別する。
2. 確認結果 — 挙動維持の判断に使ったものだけ。実行したコマンドと、そこから言えることを分けて書く
3. 未確認 — なければ「なし」
