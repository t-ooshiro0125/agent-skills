# Review Tests RSpec

## 目的と使い方

RSpec テストの回帰検知力と構成をレビューする。実行前に [review-tests](../review-tests/SKILL.md) を読み、対象範囲・手順・指摘基準・出力形式に従う。共通観点に次の RSpec 固有の観点を加え、一度のレビューとして実行する。ファイルの編集は行わない。

## RSpec 固有の確認

### example の構成と規約

- `describe` / `context` の条件と `it` の期待が対応し、結果を変える前提と検証する挙動を追えるか。階層やコメント、shared example によって条件が隠れていないか。
- `subject` が検証対象の値や処理を表しているか。`let` / `let!` の名前と値から入力や前提を追え、期待値の抽出も検証内容を隠していないか。
- 未使用の `let` / `let!`、空の example・context、検証のない example がないか。副作用を前提にする定義は、名前の参照有無だけで未使用と判断しない。
- `subject` の配置、`it` 内の準備・変数定義、`let` / `let!` と `before` の使い分け、`1 context 1 example`、expect の数などは、利用先の規約に従う。規約がなければ形式だけで違反とせず、共通の「1テスト1関心」と具体的な影響で判断する。

### 評価順序と検証対象

- `subject` の遅延評価と example 内のメモ化を踏まえ、`subject` 自体の評価と返されたオブジェクトの操作を区別し、対象処理が意図せず省略・重複していないか。
- `let` の遅延評価、`let!` と hook の実行順序、親 context からの継承・上書きを確認し、必要なデータやスタブが対象処理の実行前に用意されるか。
- `change` や例外の matcher が対象処理の実行を適切に囲み、検証の前に対象処理が実行済みになったり、別の処理の変化・例外を検証したりしていないか。
- メッセージの検証では、`expect(...).to receive` は対象処理の実行前に設定する。`have_received` は、対象メッセージを記録できる spy や stub を実行前に用意し、実行後に検証する。両者の順序を混同していないか。
- shared example / shared context と support ファイル、実行設定を読み、必要な前提・検証が実際に読み込まれるか。`pending`、`skip`、focus、タグのフィルタで必要な example が外れていないか。
- mock・stub・spy が対象の責務や必要な永続化処理を置き換えていないか。実モデル、Factory、テストダブルの選択は、利用先の規約と検証目的に合わせて判断する。

## Rails を使う場合

利用先の規約に従い、次の点を追加で確認する。Rails を使わない RSpec テストには適用しない。

- model・request・controller・job などの spec の種類が、検証したい契約と必要な統合範囲に合っているか。
- DB の読み書き、ジョブ、外部通信、検索基盤などをどこまで実物で確認するかは、利用先のテスト環境と規約に従う。DB を常に実物にする、ビュー描画を常に禁止する、といったプロジェクト固有の制約を一般化しない。
- データの後始末やトランザクション、ジョブの実行方式が前提に合い、他の example に状態を残さないか。

## 検証と報告

対象 spec と、規約に応じた RuboCop などを実行する。対象の実行コマンド、設定、必要な依存環境は利用先で確認し、特定の Rails 構成や起動方法を前提にしない。結果は共通スキルの出力形式でまとめ、RSpec 固有の指摘と共通観点の指摘を重複して列挙しない。
