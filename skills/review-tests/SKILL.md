# Review Tests

## 目的と対象

テストが必要な挙動を検証し、回帰を検知でき、保守しやすい構成になっているかを確認する。指定されたテスト・ファイル・差分を対象とし、指定がなければ現在の差分に含まれるテストを対象とする。実装、要件、既存テスト、実行設定は判断に必要な範囲で参照する。

レビューと指摘の提示までを行い、ファイルを編集しない。テストの作成・修正依頼には適用しない。RSpec を対象とする場合は、[review-tests-rspec](../review-tests-rspec/SKILL.md) の追加観点も読む。派生スキルから使う場合は、共通手順を重ねて実行せず、一度のレビューに追加観点を組み込む。

## 確認の進め方

1. 利用先にある指示ファイル・開発規約と、対象の要件・実装差分・近接するテストを読む。テストの構成、モック、実行方法に関する規約を確認し、特定の言語やプロジェクトの規約を他へ持ち込まない。
2. 変更した責務、既存の検証範囲、回帰リスクから、必要なケースと期待結果を確認する。次節の観点で、テストの記述だけでなく、実際に何を実行・検証しているかを調べる。
3. 規約と変更範囲に応じて、対象テストと適用される linter を実行する。テストの収集・呼び出しと、skip・保留・タグや設定による除外を確認し、テストの存在と実行を区別する。
4. 検知力が読み取りだけでは判断しづらい場合は、必要性と実行コストに応じてミューテーション確認を行う。実施時は隔離環境で対象の処理や保護条件を意図的に壊し、期待する理由でテストが失敗するか確認する。ユーザーの作業ツリーは変更せず、隔離環境の変更も確認後に元へ戻す。

実行や調査によるファイル・データ・外部サービスへの影響を確認し、必要に応じて一時環境を使う。実行していないチェックは明記し、実行できない場合は理由を示す。

## レビューの観点

### 挙動と回帰検知力

- 公開された挙動や契約を検証し、実装の内部手順を不必要に固定していないか。配線の検証は、そのテストで検知すべき接続に限られているか。
- 期待値に要件や具体的な結果の根拠があり、実装と同じ計算・分岐を繰り返すだけになっていないか。
- 重要な分岐、境界、失敗時の挙動を、変更の回帰リスクに応じて検証しているか。既存テストや共通ハンドラの検証を、理由なく重複させていないか。
- テスト対象の処理が実際に実行され、検証に到達するか。広すぎる例外の捕捉や、無関係な理由による失敗を期待した失敗として扱っていないか。
- モックやスタブが検証対象の処理まで置き換えていないか。実際の依存先との接続を検証する必要性と、利用先の規約に合う範囲で使われているか。

### 独立性と再現性

- 実行順序、他のケースの成功や副作用、共有する可変状態に依存していないか。連続した操作そのものを検証するシナリオと、独立すべきケースを区別できるか。
- 時刻、乱数、ネットワーク、ローカル設定や個人環境に依存する場合、その依存が検証の目的に必要で、結果を再現できるか。
- 一時ファイル、DB の状態、環境変数、モックなどがケースをまたいで漏れず、失敗時にも必要な後始末が行われるか。既存の作業環境やデータを意図せず変更しないか。

### 構成と保守性

- 1テスト1関心となり、前提・実行・期待結果を追えるか。同じ結果や契約を確認する複数の assertion は許容し、数だけを理由に分割しない。
- ケース名や条件から、守る挙動と失敗したケースを識別できるか。大量のケースを一続きにして、原因の特定や個別実行を不必要に難しくしていないか。
- 利用するテストフレームワークに適した検証方法を使い、失敗時に期待値・実際の値・対象ケースを識別できるか。表記の混在だけを理由に指摘せず、診断しやすさや検証の有効性への影響で判断する。
- 準備、fixture、helper がケースの意味を隠していないか。重複、過剰な共通化、不要なデータや処理が、変更や理解を具体的に難しくしていないか。
- 追加ケースの検知効果に対して、実行コストが不必要に大きくないか。ケース数やカバレッジの数値だけを目的にしていないか。

## 指摘の基準と出力

検知漏れ、誤った成功・失敗、不安定な結果、作業環境の破壊など、重要な回帰や安全性に関わる問題は必須修正とする。具体的な保守性・診断しやすさの改善は任意改善とする。好み、形式だけの統一、assertion 数だけの指摘は挙げず、問題がなければ無理に指摘を作らない。適用される規約への違反は、規約と影響を示す。

別のレビュースキルの一部として使う場合は、呼び出し元の対象範囲・指摘基準・出力形式に従い、その範囲の指摘だけを渡す。単独で使う場合は、次の順で出力する。

1. 必須修正 — なければ「なし」
2. 任意改善 — なければ「なし」
3. 確認結果 — 実行したコマンドと、その結果から確認できたことを分けて示す
4. 未確認 — 残った確認事項、理由、レビュー結果への影響。なければ「なし」

指摘には `path:line`、問題が成立する条件、検知できない挙動や保守上の具体的な影響を付ける。確認した事実と推測は区別し、未確認事項を検証済みとして扱わない。自分で調査できる事項は調べ、制約で残るものは明示して確認できた範囲の結果を報告する。
