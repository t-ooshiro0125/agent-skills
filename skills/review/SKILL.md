# Review

## 目的と対象

`git diff`、`git diff --cached`、PR などの差分をレビューし、挙動の変化・バグ・テストの穴に関する指摘を列挙する。必須修正と任意改善に分けて返し、修正は行わない。

## 手順

利用先の規約に従い、次の順に進める。

1. 先に、差分の性質とプロジェクトの規約に応じて機械的チェックを選択・実施し、その結果をレビューの材料にする。
   - 変更に対応するテストと linter を、選択した範囲で実行する。
   - 追加・変更したテストの構造を確認する。Rails・RSpec を使う場合の確認項目は、次節に従う。
   - 追加・変更したテストのミューテーション確認は、必要性と実行コストを考慮して実施する。実施する場合は隔離環境で対象コードを意図的に壊し、テストが失敗するかを確認する。ユーザーの作業ツリーは変更せず、隔離環境での変更は確認後に必ず元に戻す。
2. 指摘を列挙する。指摘した問題は修正せず、修正の指示を待つ。

### Rails・RSpec を使う場合

利用先の規約と差分の性質に応じて、Rails では対象 spec と RuboCop をチェック対象にする。RSpec のテスト構造では、未使用の `let`、空ブロックを確認する。`1 context 1 example` は、プロジェクトの規約で定められている場合に従う。

## 指摘の基準

- 指摘は、挙動の変化・バグ・テストの穴に関するものに限る。任意改善も同じ範囲を対象とする。
- 命名、メソッド分割、書き方の好み、リファクタ候補は挙げない。
- テスト不足は、回帰リスクが高ければ必須修正、保守性が目的なら任意改善に分ける。
- 該当する指摘がなければ、出力形式に従って「なし」と示し、指摘を無理に作らない。
- 自分が直前に書いたコードにも同じ基準を適用する。

## 出力

1. 必須修正 — なければ「なし」
2. 任意改善 — なければ「なし」
3. 確認結果 — 実行したコマンドと、そこから言えることを分けて書く
4. 未確認 — 残っている確認事項と、未確認の理由・レビュー結果への影響。なければ「なし」

指摘には `path:line` を付ける。

### 確認結果と未確認事項の書き方

- 「確定」「一致している」「存在しない」「影響なし」などの断定は、一次情報を直接読んだ場合だけにする。`grep` や `ls` の否定結果は「見つからなかった」に留める。
- 網羅性を根拠にするときは、`head` や `tail` で出力を切らない。検索パターンが漏らし得る形（パスの直書き、別の helper 名、別のアクション名、テンプレートの複製）を挙げ、それも確認する。
- テストが「存在する」ことと「実行される」ことは別に扱う。`skip`、`pending`、タグ除外がかかっていないかまで確認する。
- 実行していないチェックは明記し、実行できないチェックは理由も報告する。

自分で調べられる項目は調べてから出力する。調査では決まらない事項や、実行環境などの制約で確認できない事項が残っても、確認できた範囲のレビュー結果を報告してレビュー作業を終了してよい。その場合は、未確認事項を確認済みの事実と区別し、未確認の理由とレビュー結果への影響を明示する。レビュー作業の終了と、すべての事項の検証完了は区別し、「未確認」が空でないうちは、全面的な検証が完了したとは表現しない。
