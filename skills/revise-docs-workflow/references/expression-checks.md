# 表現ごとの確認

ユーザーの指摘と依頼範囲全体の点検で見つけた、説明が必要な用語・抽象表現を扱う。モデルが必要箇所と理解目標を選び、説明が十分か評価する。スクリプトは登録済み対象の対応漏れ、古い版、本文にない引用を検出する。難語の自動検出や全単語の登録は行わない。

## 書き換える前に登録する

選んだ読者の知識と説明量の基準で全文を読み、意味を知らないと理解できない用語、対象が分からない抽象表現、結論と理由・条件がつながっていない箇所を拾う。内容レビューで誤りが見つかったかにかかわらず点検し、依頼者が難語をすべて列挙することを前提にしない。参照できる具体的な指摘も対象へ引き継ぐ。既に明確な説明まで無理に増やさず、必要箇所に絞る。

理解目標には、その箇所を読者が説明・判断するために何を理解できればよいかを記す。用語なら必要な意味と役割、抽象的な結論なら何が足りず何の判断につながるかを具体化する。編集前に、指摘・困りごとと目標を照合する。用語の意味の不足を、その用語を使う仕組みの用途・制限だけを問う目標へ置き換えない。原文の語を使って意味を説明できるか、意味を保った分かりやすい言い換えができるかを判断する。根拠のない定義・計算法を追加せず、説明できない不足は既存の再調査・再修正・保留へ戻す。

作業本文の該当箇所を `show --unit` で取得し、引用・位置・理解目標を登録する。ID は英小文字で始め、英小文字・数字・`_`・`-` を使う。`origin` はユーザーの指摘なら `user`、点検で見つけた対象なら `inspection`。同じ節に複数あれば別 ID にする。

```json
[
  {"id": "capacity", "quote": "利用枠", "origin": "user", "goal": "何の件数に上限があり、その制約が判断にどう関わるか分かる"},
  {"id": "conditions", "quote": "適用の前提が未確定", "origin": "inspection", "goal": "どの条件が未確認で、何を確認してから採否を決めるか分かる"}
]
```

```sh
python3 revision.py --state work.json expressions --unit u0004 --token TOKEN --file expressions.json
python3 revision.py --state work.json show --unit u0004
```

引用はその対象の現行本文に存在する必要がある。同じ引用が複数あれば、先頭を0とする文字位置 `start` を指定する。位置は Unicode 文字列の索引とし、改行コードも含める。指定しなければ一意な位置を検出する。登録時の本文を `source_text` として保存し、`source` に対象 ID・引用・位置、`owners` に現在の対応対象 ID を保持する。以後の修正で元の表現が消えても登録は残る。

登録入力に結果や合否を混ぜず、ID を再利用・削除しない。理解目標の具体化は現在の `version` と理由が分かる作業記録を使い、`expression-goal --id capacity --version VERSION --goal "具体化した理解目標"` で行う。過去の目標は履歴に残り、再確認が必要になる。

読者確認で質問や目標から漏れた説明不足が見つかった場合も、この手順で対象を追加する。既存の目標が不足を捉えていなければ、回答を根拠として目標を更新し、関連するまとまりを再確認待ちへ戻す。本文が既に未確認と示している事実と、用語・理由・条件の説明不足を分けて記録する。

## 現行本文を読んで結果を保存する

まとまりの計画・編集を終えて現行本文を取得し、`required_expressions` の各 ID・理解目標・`version` を読む。説明が別の段落にあればその対象も取得する。説明箇所を引用し、何を読み取れたかを別入力へ記す。引用の `token` には、引用先の `target.content_token` を使う。これは本文・文脈・計画の版で、他の表現結果を保存しても変わらないため、同時に点検した複数の結果を順に保存できる。

```json
{
  "outcome": "explained",
  "observation": "本文は一日あたりの送信件数を上限の対象とし、超える利用案には確認が必要だと説明している",
  "evidence": [
    {"unit_id": "u0004", "token": "説明箇所を点検した時のcontent_token", "quote": "一日に送信できる件数には上限がある。"},
    {"unit_id": "u0007", "token": "別の説明箇所を点検した時のcontent_token", "quote": "上限を超える利用案は、対応可能か確認してから採否を決める。"}
  ]
}
```

```sh
python3 revision.py --state work.json expression-check --id capacity --version VERSION --file expression-result.json
```

`evidence` は空にせず、現行の対象 ID・点検時の content_token・引用を指定する。同じ引用が複数なら `start` も指定する。別段落の説明を使ってよく、元の単語を削除したり一定量を書き換えたりする必要はない。本文にない説明を引用した結果は拒否する。説明がまだない場合は、不足を確認できる現行の表現や周辺を引用する。

| outcome | 記録する内容 |
| --- | --- |
| `explained` | 現行本文の説明で理解目標を満たすと判断した観察内容 |
| `unchanged` | 観察内容に加え、現在の説明で足りる `reason` |
| `needs_revision` | 読み取れない内容を示し、次の修正・確認へ戻す |
| `held` | 観察内容と `reason`・`proposal`・`required_decision`。不足する根拠、具体案、必要な確認・判断を残す |

表現ごとの結果をすべて保存してから、[まとまり全体の結果](work-state.md#修正後に別入力で確認結果を保存する)を `record` で保存する。登録が A・B の2件あれば、A の結果だけでは受け付けない。個別の表現が未解消なら全体も再修正または保留とし、全体を `confirmed`・`unchanged` にできない。上限で保留にする場合、未解消の表現すべてにも具体案・理由・必要な判断を付けた `held` を保存してから全体を記録する。表現の結果だけで次の編集へ進めず、まとまりの確認回数による上限も維持する。

## 変更と構成整理の後に再確認する

`version` は登録内容・現在の対応対象の本文と文脈・計画に結び付く。説明引用は入力時の現行 content_token と位置で検査する。互換性のため、その時点で有効な対象の token も受理する。表現結果の保存は、他の表現の content_token を古くすることなく、対応するまとまりの token を更新する。全表現の結果を保存した後にまとまりを取得し直し、その結果も読んでまとまり全体を点検する。本文・読者設定・理解目標・説明箇所が変わったら再読し、古い結果へ最新の版だけを付け直さない。表現の結果を変更した場合も、既存のまとまりの合格を使い回せない。

分割・結合は ID、登録時の引用と位置、確認履歴を維持し、旧対象を置換したすべての対象を `owners` にする。説明の移動先を自動で意味判定しないため、分割後は複数の対象で同じ表現の確認が必要になる場合がある。結果は全体で1件を共有できるが、対応対象と引用先の現行版で取り直す。並べ替えでも ID を落とさず、変わった文脈を確認する。

表現に保留があれば対応対象の `hold_active` にも反映し、`next` は飛ばす。新しい根拠や判断を得た後、対応する対象への理由付き `invalidate` で解除して再確認する。依頼条件の更新だけでは保留を解除しない。保留した表現は結果へ含め、`fully_resolved: false` として解決済みと区別する。

旧形式2の状態に登録欄がなければ空として読める。再開時には依頼・本文を点検して必要な表現を登録し、過去の節全体の合格を個別表現の合格へ転用しない。引用の実在と記録の充足は、説明の正しさや読者の理解を証明しない。重要箇所は SKILL.md の読者確認と原文照合を行う。
